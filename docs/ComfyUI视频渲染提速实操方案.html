① 一句话诊断

你的环境其实很新，不用重装。体检确认：PyTorch 2.9.1 + CUDA 13.0、ComfyUI 0.39.0（内置 Comfy Compiler / CUDA graphs 自 2026-09 起默认开启），GPU 识别为 sm_120（Blackwell）、支持 bf16。50 系的核心加速前提（cu130、NVFP4 硬件加速）已经全部就位——网上大量"50 系要先升级 cu130"的教程对本机不适用，直接跳过。

三套工作流的优化程度严重不均：

  • H3（10-13 分钟）＝"裸奔"：保存的 r2v/i2v 工作流里 steps=20、无任何加速节点（没有 SageAttention、没有分块/缓存节点）。这是三套里最慢、也是水分最大的。
  • Wan REMIX flf2v（约 4 分钟）＝已经很卷：fp8_e4m3fn 双专家 + WanMoeKSampler 6 步 + lightx2v 4 步蒸馏 LoRA + wanBlockSwap×2 + fp16 累加 + sage_attention=auto。可再抠的只剩"确认 sage 是否真生效"和叠加 TeaCache。
  • LTX 2.3（较快）＝已经优化：distilled fp8_scaled + 13/4 步双 pass + ChunkFeedForward + 分块 VAE 解码 + latent 超分。注意「稳定版」那份工作流用的是 dev（非蒸馏）权重，还有 NVFP4 变体可换。
最优先三件事（做完 H3 预计从 10-13 分钟降到 5 分钟上下，数字待实测）：
① 给 H3 装上 SageAttention（官方口径"roughly double"，约 2×，几乎无损）；
② H3 上官方 8 步 turbo LoRA / FastH3 蒸馏版（20→8 步，约 2.5×，轻微损失）；
③ 确认 Wan/LTX 的 sage_attention 是真的生效了（先查 pip 里有没有 sageattention 包，再看启动日志）。

③ 方向一：模型层加速（量化/蒸馏/缓存）

1. lightx2v 4 步蒸馏 LoRA（Wan2.2 首选）轻微有损P1
原理官方把 Wan2.2 蒸馏到 4 步，用低/高噪声双 LoRA 加速，无需换模型。 操作你已在用（wan22 系列工作流已挂高低噪配对）。核对：T2V 用 Wan2.2-T2V-A14B-4steps-lora-rank64-V1；I2V/FLF2V 必须高低噪各挂一个：wan2.2_i2v_lightx2v_4steps_lora_v1_high_noise + ..._low_noise，步数设 4。 收益官方文档定性"从 20+ 步降到 4 步"；官方 4090D 实测（Wan2.2 Fun-Control，fp8_scaled）：524s→138s（首跑约 3.8×）、520s→79s（二次约 6.6×）。5060Ti 上你的 flf2v 已 6 步，再压到 4 步约再省 30%（待实测）。 质量轻微：细微运动细节/高频纹理略降，静态镜头几乎无感。 风险高低噪 LoRA 必须配对；CFG 需配合蒸馏调度（你已是 cfg=1，正确）；别叠加第二个加速 LoRA。
来源：docs.comfy.org/tutorials/video/wan/wan2-2-fun-inp（LoRA 文件名与配对规则）· docs.comfy.org/tutorials/video/wan/wan2-2-fun-control（4090D 实测 138s/79s）· lightx2v 中文文档
2. H3 官方加速三件套（SageAttention / Comfy Kitchen / 稀疏注意力 / FastH3）轻微有损P1
原理H3 慢在注意力层；SageAttention 用低比特量化注意力替换标准注意力（官方明示可"约 2 倍速"）；FastH3 是官方蒸馏检查点（8 步 vsa 模式）；稀疏注意力跳过不重要的 key block。 操作① 装 SageAttention：从 SageAttention Releases 下载与 torch/CUDA 匹配的 Windows wheel（本机 torch 2.9+cu130，选对应版），在整合包 python 环境 pip install <wheel>；② 工作流在 UNETLoader→BasicGuider 之间插 Patch Sage Attention KJ（KJNodes，sage_attention=auto），或启动器加 --use-sage-attention；③ 若用 bf16 权重出片尾 morphing/花字，换 Comfy Kitchen attention（--use-ck-attention，0.32+）或 Model Attention Backend 节点；④ 长镜头试内置 Model Sparse Attention（sol-attn，tau≈1.3，start_percent=0.2）；⑤ 0.36+ 直接用 FastH3 模板（8 步）。 收益官方原文 SageAttention "roughly double the generation speed with minimal quality loss"（≈2×）；5060Ti 社区实测：H3 8 步约 50s/步、10 秒片 494s，比纯分块 111s/步快约 2.2×（掘金帖）。你的 10-13 分钟 → 约 5-7 分钟（叠加 turbo LoRA 更低，待实测）。 质量Sage INT8 kernel 在片尾可能出现 morphing/花字（官方明示），换 bf16 权重 + ck-attention 可解；默认 int8_convrot 权重不兼容 ck-attention（issue #15529 会崩），此时保持默认注意力或换 bf16 权重。 风险sage wheel 与 torch 版本错配会静默回退普通注意力（控制台有提示属正常）；int8_convrot 权重用 ck-attention 会崩溃——别照搬网上的 ck-attention 教程不区分权重。
来源：docs.comfy.org/tutorials/video/minimax/minimax-h3（官方，已核实原文）· pypi.org/project/sageattention/2.2.0（wheel）· ComfyUI issue #15529 · juejin.cn/post/7672711130194395176（5060Ti 实测）
3. WanVideo TeaCache（kijai wrapper 内置，Wan2.2 缓存复用）轻微有损P2
原理相邻步输出变化小于阈值时跳过该步前向、复用上一步缓存，省模型前向次数。 操作在 kijai WanVideoWrapper 工作流加 WanVideo TeaCache 节点：选 Wan2.2 MoE 对应系数，阈值保守起步；起始步不要跳过（early steps never skip），否则运动崩坏。 收益社区定位为与 SageAttention / torch.compile 叠加的"标准三件套"之一，单节点约 1.5-1.8×（4090 口径；5060Ti 待实测）。 质量轻微；阈值过激进→运动拖沓、帧间抖动。 风险只省前向不省显存；与 6 步超短 schedule 叠加时收益会缩水（可跳步本来就少）。
来源：github.com/kijai/ComfyUI-WanVideoWrapper · comfy.org 节点页 · 备注：独立 TeaCache 节点（welltop-cn）支持矩阵是 Wan2.1/LTX-Video(0.9)/HunyuanVideo/CogVideoX，不支持 Wan2.2、不支持 H3，见 deepwiki 支持矩阵、stable-diffusion-art.com/teacache
4. LTX 2.3 NVFP4 变体（50 系专用）轻微有损P2
原理NVFP4 是 Blackwell 原生的 4bit 浮点格式，只有 cu130 的 torch 才能硬件加速（本机已满足）。 操作在 ComfyUI 模板浏览器/模型库换用 LTX-2.3 的 NVFP4 权重（Lightricks 官方发布，配 ComfyUI-LTXVideo 节点栈），FP8 变体次之。 收益NVIDIA 官方博客（RTX 50 系）：NVFP4 最高 2.5× 性能、显存 -60%；FP8 最高 1.7×、显存 -40%（测试在 RTX 5090 上）。5060Ti 具体倍数待实测。 质量轻微：4bit 格式，官方称质量损失极小。 风险必须 cu130（本机已是）；NVFP4 文件需从官方渠道下载，别混用 fp8 文件。
来源：blogs.nvidia.cn（官方，已核实"2.5×/60%"原文）
5. GGUF（city96）——仅当显存吃紧不提速·待实测
原理K-quants 把高/低噪双专家权重压到约一半体积，运行时反量化。主作用是显存而非速度。 操作Manager 装 city96/ComfyUI-GGUF；Wan2.2 A14B 有官方教程点名的 GGUF（HuggingFace bullerwins 系列），用 UnetLoaderGGUF 分别拉高低噪两文件（档位必须一致：Q4_K_M 起步、Q5_K_M 质量档）。 收益社区共识 Q8 视觉与 fp16 无差，但 5060Ti 上 GGUF 反量化 kernel 与 fp8 对比无公开数字，待实测，大概率不显著快于你现在的 fp8。 质量Q4 轻微～中等（细节略软），Q5 轻微。 风险FLF2V 无独立 GGUF 文件（只有 I2V/T2V-A14B）；H3、LTX 无 GGUF 量化包，不可用。
来源：docs.comfy.org/zh/tutorials/video/wan/wan2_2 · github.com/city96/ComfyUI-GGUF
6. Nunchaku int4/NVFP4（SVDQuant）——当前不适用不适用
结论当前 nunchaku 官方支持列表只有 FLUX.1、Qwen-Image、SANA、Z-Image，不含 Wan 2.1/2.2、H3、LTX 任何视频模型。网上 2025 年"nunchaku 跑 Wan2.1"的教程指向旧分支，别照搬。等官方放出视频 4bit 权重再考虑。 风险Windows 编译 wheel 门槛高（需 CUDA≥12.8、VS Build Tools）；Blackwell 侧 CI 已适配（含 RTX 5090，NVFP4 较 BF16 约 3× 是 FLUX 数据）。
来源：github.com/nunchux-ai/nunchaku（README 支持列表）

④ 方向二：编译层

1. ComfyUI 内置 Comfy Compiler + CUDA graphs无损P1
原理aimdo 内存编译器提前算定显存分配 + 原生 CUDA graphs，消除分配抖动、让每步跳过低开销。不是 torch.compile。 操作本机已具备（ComfyUI 0.39.0，0.35+ 默认开），无需任何操作。仅当崩溃/与自定义节点冲突时在启动参数加 --disable-comfy-compiler 或 --disable-cuda-graphs 回退；用 --assert-graph-breaks 诊断。 收益步间开销下降；官方 changelog 未给倍数 → 待实测。 质量无损失（不改数值）。 风险个别老 LoRA 链可能触发图断裂崩溃，回退即上面两个 flag。
来源：docs.comfy.org/development/comfyui-server/startup-flags · docs.comfy.org/changelog
2. torch.compile（内置 TorchCompileModel 节点）无损P2
原理torch.compile(inductor) 包 UNet forward，首跑编译、之后走编译图；首次编译耗时几分钟，改 LoRA 栈后需重编译。 操作工作流加内置 TorchCompileModel（或社区 TorchCompileSpeed）节点，插在 UNETLoader→采样之间，mode 用 default 或 max-autotune-no-cudagraphs。本机 torch 2.9.1+cu130 满足 Blackwell 要求。 收益社区实测"100 帧 35-50 秒、快 2-3 倍、显存 12G 不变"（CSDN 帖，未注明显卡型号）；5060Ti 待实测。 质量轻微（inductor 纯算子融合，数值等价）。 风险编译缓存路径含中文/空格可能失败；与部分自定义节点不兼容崩溃时删节点回退。
来源：docs.comfy.org/built-in-nodes/TorchCompileModel.md · CSDN 实测帖 · rentry.org/wan21kjguide（50 系 cu128/cu130 命令）
3. 启动参数 --fast（fp16 累加 / fp8 矩阵乘 / cublas_ops）轻微有损P2
原理启动级算子加速开关；fp16_accumulation 就是社区说的 fp16_fast。 操作绘世启动器高级选项加 --fast（或 --use-sage-attention 一并加）；控制台须显示 "Enabled fp16 accumulation" 才生效。注意：你的 Wan 工作流已在 loader 层开了 fp16_accumulation=true，全局 --fast 主要惠及 H3/LTX。 收益配合 SageAttention 是社区 Wan 提速标配；单独倍数未溯源 → 待实测。 质量轻微（官方标注 experimental、may affect quality）。 风险出图异常先删 --fast 排查；依赖 torch 版本匹配（本机 cu130 OK）。
来源：docs.comfy.org/development/comfyui-server/startup-flags
4. SageAttention v2（编译/算子层最优解之一）轻微有损P1
原理低比特量化注意力替换标准 SDPA；注意力占视频扩散大头，故提速明显。 操作① 从 SageAttention Releases 下载与 torch/CUDA 匹配的 Windows wheel（本机选 cu130/torch2.9 对应版，abi3 通用 wheel 可跨 py3.10-3.13）；整合包 python 里 pip install <wheel>；② 全局：启动器加 --use-sage-attention；或工作流加 KJNodes 的 Patch Sage Attention KJ（H3 插在 UNETLoader→BasicGuider 之间，sage_attention=auto）。Blackwell 另可试 ComfyUI-SageAttention3（pip install sageattn3）。 收益官方 H3 文档："roughly double the generation speed with minimal quality loss"（约 2×）；5060Ti Wan 实测（81 帧 720p）：Sage1 5分40秒 → Sage2 4分58秒 → Sage3 4分51秒（Sage2/3 比 Sage1 快约 25%）。 质量轻微；H3 的 INT8 kernel 片尾 morphing/花字→换 bf16 权重 + Comfy Kitchen attention 解决；R2V 多参考大显存机器有"开了发糊"的社区报告。 风险需要 fp16/bf16 张量，部分层自动回退标准注意力（正常）；先确认本机是否真的装了 sageattention 包——Wan/LTX 的 loader 里 sage_attention=auto 在无包时静默回退。
来源：docs.comfy.org（H3 官方文档，已核实） · pypi sageattention · github.com/wallen0322/ComfyUI-SageAttention3 · 5060Ti 实测见方向七表格
5. OneDiff / CTranslate2 / TensorRT —— 本机不适用（已核实）不适用
OneDiff上游明确 Windows 仅支持 WSL2 运行（onediff 1.2.1.dev19 PyPI 说明）；秋叶整合包是 Windows 便携 Python，套 WSL 等于另起环境，不兼容 → 跳过。 CTranslate2/Faster-*为自回归 LLM/whisper 设计；Wan/H3/LTX 是 flow-matching 扩散 DiT（序列动态变化、CFG 双路、自定义注意力），架构上无可复用方案，不值得装。 TensorRT官方 ComfyUI TensorRT 节点只覆盖 SDXL/SD3/FLUX 图像模型；TensorRT-LLM 里的 Wan2.1-I2V 是数据中心管线，非 Windows 本地 ComfyUI 可走的路。
来源：pypi onediff（"use it under WSL"）· TensorRT-LLM 支持列表

⑤ 方向三：采样层（步数/CFG/采样器）

1. H3 官方采样参数基线（res_multistep + simple）看档位P1
原理H3 官方模板指定采样器/调度器组合，步数决定质量-速度平衡点，与 CFG 无关（BasicGuider 无 CFG 概念）。 操作保持 KSamplerSelect=res_multistep + BasicScheduler=simple（你已是）。步数档位：简单内容 12-16 步够用；高频细节（链甲/花纹/小物件堆）到约 50 步还在变好；音轨比画面收敛慢，8 步时人声音色最弱，12 步以上才可用。 收益你保存的 H3 工作流是 20 步。20→16 步省约 20%，20→12 步省约 40%（5060Ti 绝对秒数待实测）。 质量12-16 步对多数镜头可接受；R2V/参考类镜头别用 4 步（官方明示参考几乎不生效、人脸/姿态漂移），紧盯参考回 20-25 步。 风险步数再低（<12）画面细节与音轨同步劣化。
来源：docs.comfy.org/tutorials/video/minimax/minimax-h3（官方文档，已核实）
2. H3 官方 8 步 turbo LoRA / FastH3 蒸馏版轻微有损P1
原理模板内置 Enable Lightning LoRA（turbo_mode）：T2V/I2V 从 20 步降到 8 步，R2V 降到 4 步；FastH3 是官方蒸馏检查点（8 步 vsa，0.36+ 模板直接有）。 操作H3 工作流里打开模板的 Enable Lightning LoRA 开关（或加载对应 turbo LoRA）后 steps 改 8；或直接用 FastH3 模板。 收益步数 20→8 ≈ 2.5×；与 SageAttention 叠加理论近 4-5×（待实测）。社区参考：秋叶整合包 H3 实测 4 步 LoRA 后 21 分钟→13 分钟（未写明设备）。 质量轻微；R2V 紧参考镜头的 4 步档官方明确警示（参考几乎不生效），此类镜头回 20 步。 风险turbo LoRA 与普通 LoRA 叠加需测试；8 步时音频质量仍需 12 步以上档位复核。
来源：docs.comfy.org（官方，已核实） · 秋叶 H3 实测见方向七表格（抖音链接）
3. Wan2.2 采样：你现在 6 步已是"低步数终点"，别再加戏保持现状
结论官方 flf2v 模板两段式（高低噪声段各 4 步、uni_pc+beta、CFG 1），社区推荐区间 CFG 3.5-5 / euler；你已经用 WanMoeKSampler 6 步 + cfg=1/1 + euler_ancestral + lightx2v 4 步蒸馏 LoRA——这是社区标准加速形态。再降步数会明显崩质量；本方向对 Wan 无进一步无损空间。 注意CFG 拉高会增加伪影；motion_amplitude=1.15（PainterI2V）已设，运动幅度越大越要保帧数而不是降帧数。
来源：comfyui-mcp wan-flf skill · comfy.org 官方 flf2v 工作流 · WanMoeKSampler 文档
4. LTX 2.3：8 步是蒸馏版设计工作点看档位
结论蒸馏版官方即 8 步固定（euler，细化/放大段 CFG=1）；完整（dev）模型 30-50 步。你的 ltx_t2v_720p 用 distilled + 13/4 步双 pass，已合理；「稳定版」那份用 dev 权重——换成 distilled 权重后步数可大幅下降（对照 dev 30-50 步）。再压 8→6 步质量下降（待实测）。 RESTARTLTX-2.3 官方 API 带 use_restart_sampling 开关（每步注入小噪声改善质量）；ComfyUI 侧用 ComfyUI-Restart-Sampling 节点。代价是等效多跑几轮——是"8 步发糊时补质量"的手段，不是纯提速。
来源：fal.ai LTX-2.3 API 文档（restart 开关）· comfy.icu KRestartSamplerAdv
5. "RAD=8" 出处核查结论无出处
结论未找到 "RAD=8" 作为具名社区配方的可追溯出处（Reddit/4chan/中文社区检索无对应帖），不编造。最接近的可溯源低步数技巧就是：H3 turbo 8 步、Wan lightx2v 4 步蒸馏 LoRA、两段式高低噪声采样（你已全部在用或可加）。

⑥ 方向四：帧数/时长策略

1. H3 帧数吸附：17k+5，固定 24fps无损P1
原理H3 时间维按 17 帧一块处理，合法总帧数只能是 17k+5：5/22/39/56/73/90/107/124/141/158/175/…；固定 24fps（严格校验 ±0.01），官方时长规格 4-15 秒。你的 175 帧=17×10+5≈7.3 秒，正是合规值；15s 版 362 帧=17×21+5 也合规。 操作别在秒数上精调（5.0→5.1 吸附后可能是同一档）。要省时间就下踩一整档 17 帧：175→158（6.6s）或 141（5.9s）；要确定时长，先定 17k+5 帧数再 ÷24 回填秒数。 收益帧数≈线性影响采样耗时：每少 17 帧省约 1/10 推理时间。参考 4090 上 124 帧 640×1152 端到端 120.9s（20 步含 VAE）。5060Ti 绝对秒数待实测。 质量无损（只是镜头短 0.7s/档）。 风险低于 124 帧后动作易截断；别越过 4-15s 规格。
来源：iqilian.com（17k+5 详解） · minimax.io 官方发布 · besthub.dev H3 本地运行
2. Wan 帧数网格：4n+1（"16n+1"是更保守的超集）无损P2
原理Wan VAE 时域 4× 压缩，帧数需满足 (帧数−1) 被 4 整除，即 4n+1：…49/77/81/121…。你工作流里的 $DURATION×16+1（5s→81 帧）落在 16n+1 网格——它是 4n+1 的合法超集，不出错但偏保守；kijai wrapper 以 81 帧窗为常用单元。 操作短镜可试 4n+1 最小合规档：49 帧（16fps≈3s）比 81 帧省约 40% 采样；81 帧（≈5s）是推荐工作点；121 帧（≈7.5s）显存大增慎用。flf2v 与 t2v 同网格；flf2v 只多两次 CLIP Vision 关键帧编码（一次性开销，远小于采样），显存画质同档，优势是首尾可控、减少返工。 质量无损（帧数合规即可）；49 帧动作偏赶，复杂运镜建议 81 帧。 风险Wan2.2-TI2V-5B 宽高需 32 倍数（2.2 VAE 16× 空间压缩）；REMIX flf2v 配 lightx2v 蒸馏 LoRA 时帧数离训练分布太远可能崩运动（需实测）。
来源：utensils.io/mold/models/wan.html（4n+1 网格） · comfyui-mcp wan-t2v skill · kijai WanVideoWrapper readme
3. LTX 帧数：8n+1，最短 25 帧无损P3
操作LTX VAE 时域 8× 压缩，video_frames 须满足 8k+1：25/121/241…。短镜直接取 25 或 121，别填中间数。你的 361 帧=8×45+1 合规。 风险内部 fps=60 与 VHS 输出 fps=25 不一致，建议统一（LTX 原生 60fps 训练、输出 25fps 播放时确认帧率转换节点设置）。
来源：docs.qvac.tether.io（8k+1 约束）
4. 帧数 vs 耗时的总规律无损
结论渲染耗时 ≈ 随（latent 帧数 × 分辨率 × 步数）线性增长。合规网格上"下踩一整档"是无画质损失的省时间手段，比降步数更划算。工作流层面：把 H3 的 175 帧按镜头实际需要压缩到 141/158，把 Wan 短镜压到 49-57 帧（4n+1），每档都实打实省时间。

⑦ 方向五：并行与显存

1. 单卡 16G：不要队列并行/多开不推荐
结论ComfyUI 单实例本串行执行；多开实例可并行，但视频扩散已吃满显存与 CUDA 引擎，正片渲染并行只会更慢/ OOM。最多错峰用：一个实例出草稿、一个实例跑正片，且正片保持单实例队列。 pipeline/tensor parallelComfyUI 的 MultiGPU/pipeline parallel 要求多张同型号 GPU（官方测最快 1.95×）；tensor parallel 需跨设备切分通信——单卡完全用不上，别装这类节点。
来源：docs.comfy.org MultiGPU_WorkUnits · dev.to 单卡并行实测
2. 显存策略：常驻 + 动态显存 + 桌面预留无损P2
原理新版 ComfyUI 动态显存让模型常驻显存、不卸回 RAM（省 PCIe/DDR 往返）；--reserve-vram 给系统/桌面留缓冲防 OOM。 操作① 绘世启动器加 --reserve-vram 1.5（Windows 桌面合成预留）；② 若一条镜头重复跑、显存够，加 --highvram 让模型常驻免重载（16G 跑 H3 时反而别加，会挤爆分块）；③ 别用 --lowvram/--novram（4-8G 卡用的，会拖慢）；④ H3 分块加载时，采样完、VAE 解码前插一个"清缓存/卸载全部模型"屏障节点（你已装 memory_cleanup），腾显存再装双 VAE。 收益消除模型反复重载与 offload 抖动；5060Ti 上 H3 纯分块 111s/步 vs Sage 8 步 50s/步（含调度差异，见方向一）。 质量无损。
来源：docs.comfy.org 启动参数 · blog.comfy.org 动态显存
3. 精度取舍：别加 --force-fp16无损（防翻车）P2
结论H3 按 bf16/int8（int8_convrot）发布，强转 fp16 有 NaN/黑屏风险；保持官方量化权重。真正无损加速靠 SageAttention 的 int8/fp8 attention kernel 与 NVFP4（cu130 硬件加速）。fp8_scaled / int8_convrot / nvfp4_awq 都是"官方档位"，比手动 --force-fp16 安全得多。 注意功耗墙压到 150W 只慢 3%（5060Ti 实测 510s vs 494s）还降温——若显存温度高可考虑，与提速无关。
来源：juejin.cn 5060Ti H3 实测
4. 环境版本核查结论（cu130 已就位，无需折腾）已满足
结论网上"50 系必须升 cu130"的教程对本机不适用：torch 2.9.1+cu130 已含 sm_120 内核、NVFP4 可硬件加速。唯一要做的是保持 ComfyUI 与关键节点更新（Manager 里只更新核心 ComfyUI 与必要加速节点；KJNodes/第三方大节点整包慎升，更新前备份 custom_nodes）。
来源：blog.comfy.org 新优化公告 · aiqnahub 5060Ti 升级评估

⑧ 方向六：输出管线

1. VHS 全工作流换 NVENC 硬编码无损P2
原理你的三套工作流输出都是 VHS video/h264-mp4＝libx264 CPU 编码；换 video/nvenc_h264-mp4（或 nvenc_hevc）走显卡 NVENC 编码单元，几乎不占采样算力。 操作VHS_VideoCombine → format 选 video/nvenc_h264-mp4；该格式下质量控件是 bitrate（Mbps）而非 crf，建议 20-40 Mbps（60Mbps 近无损档）；pix_fmt=yuv420p；frame_rate 填实际帧率。注意 VHS 的 nvenc 格式不暴露 faststart，网页秒开需外部重封装。 收益编码阶段从 CPU 数十秒级压到秒级；占总耗时比例待实测（渲染主导）。 质量同码率 NVENC 略逊 libx264，但 crf≈19 视觉档目视无损；hevc 同质量更省码率。 风险驱动/FFmpeg 不带 nvenc 时该格式不出现（装 imageio-ffmpeg）；50 系需较新驱动；nvenc 格式无 faststart 开关。
来源：numonic.ai VHS 参数表 · NVIDIA NVENC FFmpeg 文档
2. 外置 ffmpeg NVENC 压制（PNG 序列方案）无损P3
原理VHS 存无损 PNG 序列（video/8bit-png），渲染与编码解耦，后期一次性压制。 命令模板（已按 FFmpeg 源码校正）# 注意：h264_nvenc 的质量档是 -cq 不是 -crf（-crf 会被忽略） ffmpeg -framerate 24 -start_number 0 -i frame_%05d.png -c:v h264_nvenc -preset p5 -rc vbr -cq 19 -pix_fmt yuv420p -movflags +faststart out.mp4 # 合并 TTS 音频： ffmpeg -framerate 24 -i frame_%05d.png -i audio.wav -c:v h264_nvenc -preset p5 -rc vbr -cq 19 -pix_fmt yuv420p -c:a aac -shortest out.mp4 参数说明preset p1 最快质量最低 → p7 最慢质量最好（默认 P4，近线性）；cq 19≈libx264 crf 19 视觉档；+faststart 网页秒开；帧从 0 编号时加 -start_number 0。 收益175 帧 PNG 序列 NVENC p5 压制通常数秒完成（待实测）。 风险分辨率必须偶数（640×1152 合规）；老驱动不支持 hevc_nvenc 时退回 h264_nvenc；PNG 序列占盘大（每帧约 1-2MB）。
来源：ffmpeg.org nvenc_h264 源码（cq/preset/rc 选项表） · NVIDIA Video Codec SDK 10 presets 博客
3. 草稿低分辨率 + 后超分（返工率最高的大头）有损（画面后处理）P2
原理扩散采样耗时随像素近似平方增长；先出低分辨率草稿定镜头，定稿再单次超分，避免"正片废帧重渲染"。 实测Wan2.2 14B fp8+4 步（V100 16G，5 秒片）：832×480 ≈178s，1280×720 ≈15分12秒——像素仅 2.2×，耗时约 5×。官方视频放大页：FlashVSR 本地 4K 约 52s；SeedVR2（5090）1080p 约 312s；SeedVR2 在 12GB 卡超分 10 秒片需 35-45 分钟（社区实测）。 操作出片按 640×1152 或更低草稿跑、定镜头；定稿走 LTX 原生 2x 空间放大器（你已有 latent 超分）或 FlashVSR。 质量超分对运动模糊帮助有限；SeedVR2 在 16G 卡上耗时需实测。
来源：CSDN 分辨率-耗时实测 · docs.comfy.org 官方视频放大
4. VHS 常见坑速查防坑
  • 格式下拉只有 GIF/WebP → FFmpeg 未被识别，装 imageio-ffmpeg；
  • 预览黑屏但文件能播 → 用了 h265/10bit，换 h264+yuv420p；
  • 音频不同步 → 时长应为 帧数÷帧率，用 trim_to_audio 开关；
  • 报 "Got unsupported ScalarType BFloat16" → 上游 VAE 输出转 fp16；
  • frame_rate 必须是单值，接列表报 "unable to parse option value as video rate"；
  • 长片 OOM → 挂 VHS_BatchManager。
来源：numonic.ai · VHS README

方案排除原因
onediff / nexfortWindows 仅 WSL2 支持，与秋叶整合包（Windows 便携 Python）不兼容（PyPI 官方说明）
TensorRT官方节点只覆盖 SDXL/SD3/FLUX 图像模型；TensorRT-LLM 的 Wan 是数据中心管线，非本地 ComfyUI 路径
CTranslate2 / Faster-*为自回归 LLM 设计，扩散 DiT 架构无可复用方案
nunchaku int4（SVDQuant）官方支持列表不含任何视频模型（仅 FLUX/Qwen-Image/SANA/Z-Image）；等官方放 Wan 4bit
GGUF 提速（city96）仅 Wan A14B I2V/T2V 有官方 GGUF，无 FLF2V/H3/LTX；作用是显存不是速度，Blackwell 上对 fp8 无提速证据
独立 TeaCache 节点（welltop-cn）支持 Wan2.1/LTX-Video(0.9)/HunyuanVideo/CogVideoX，不支持 Wan2.2、不支持 H3；Wan2.2 用 kijai 的 WanVideo TeaCache
队列并行 / 多开实例单卡 16G 视频任务并行必 thrash/OOM，正片无收益
pipeline / tensor parallel需多张同型号 GPU，单卡不可用
升级 torch 到 cu130本机已是 torch 2.9.1+cu130，无需再动
--force-fp16H3 按 bf16/int8 发布，强转有 NaN/黑屏风险

⑫ 风险与 OOM 防护

  • 先备份再动环境：装 wheel / 更新节点前，备份整合包 custom_nodes 与 python 环境（或记下当前版本号可回滚）。
  • sage wheel 与 torch 版本必须匹配（本机 torch 2.9.1+cu130）：错配不会报错，只会静默回退普通注意力——务必看启动日志确认 "SageAttention" 字样。
  • H3 int8_convrot 权重不兼容 ck-attention（issue #15529 崩溃）：用默认注意力或换 bf16 权重再切。
  • 编译节点（torch.compile）首次编译耗时几分钟、改 LoRA 需重编译；路径含中文/空格可能失败；崩溃就删节点回退。
  • OOM 防护组合：--reserve-vram 1.5 + 采样后 VAE 解码前加 memory_cleanup 屏障节点 + H3 分块加载别叠加 --highvram。
  • LTX 的 ReservedVRAMSetter 已设 1.5GB/0.8GB：换 NVFP4 后显存占用下降，可适当调小预留提速。
  • 更新策略：Manager 只更新核心 ComfyUI 与必要加速节点；KJNodes 等大节点整包慎升（易改旧行为），更新前备份。
